## 工作区情况

工作区是本地项目文件夹，绝对路径不公开。开始时该目录为空，并且不是 Git 仓库。后续生成的交付物分布在三个主要目录中：

## 上游项目学习过程

我先学习了 GitHub 上的 `librespeed/speedtest` 项目。重点阅读了项目说明、Docker 说明、官方 Dockerfile、官方入口脚本、前端测速控制代码、测速工作线程和 PHP 后端接口。

学习后的判断是：LibreSpeed 的测速能力完全建立在 HTTP 请求上。下载测速靠随机数据接口，上传测速靠空接收接口，延迟和抖动靠多次空请求采样。因此，要实现 VPS 到 VPS 的测速，不需要引入新协议，也不需要破坏原有网页测速逻辑，只要让服务器端代理去主动访问另一台服务器的原版后端接口即可。

## 官方服务部署过程

官方 LibreSpeed 服务部署在授权固定端的独立 Web 端口，与后续增强服务隔离。实机地址和端口不公开，部署脚本是 `shell_script/deploy_librespeed.sh`。

第一次部署时，远端系统是 Debian 13，默认软件源没有 `docker-compose-plugin` 包，脚本在安装 Docker Compose 插件时失败。这个失败说明脚本不能把 Compose 插件当成强依赖。随后我修改脚本，使它在 Docker Compose 可用时使用 Compose，不可用时自动回退到 `docker run`。

第二次部署成功。脚本安装了 Docker，拉取官方镜像 `ghcr.io/librespeed/speedtest:latest`，启动名为 `librespeed` 的容器，并把容器内 `8080` 端口映射到用户指定的宿主机端口。远端本机检查和本地外部访问检查都返回了正常 HTTP 响应。

## 魔改服务实现过程

魔改项目放在 `new/project`。它不是重写 LibreSpeed，而是在官方镜像基础上增加服务器间测速能力。

新增的 `vps-agent` 目录包含三个对外接口和一个公共文件。公共文件负责令牌校验、目标地址规范化、下载测速、上传测速、延迟采样和远端 JSON 调用。健康接口用于确认代理可用。单向测量接口用于让当前 VPS 测量目标 VPS。双向编排接口用于让固定端一次性完成两个方向的测量。

新增的 `vps.html` 页面提供浏览器入口。用户可以输入固定端地址、测试端地址、代理访问令牌和测试参数，然后从页面上触发双向测试并查看 JSON 结果。

为了保留原版功能，我没有删除原版首页、现代页面、经典页面、稳定性测试页面或原版后端接口。魔改版容器启动后，仍然可以正常访问原版 LibreSpeed 页面，也可以访问新增的双 VPS 测速页面。

## 双 VPS 部署和验证过程

魔改版分别部署到已授权固定端 A 和测试端 B；实际地址和端口只在本地留存。两端容器名称都是 `librespeed-vps`，并使用 Docker 自动重启策略。

部署过程中曾出现 Windows 换行符导致容器入口脚本无法执行的问题。原因是本地工作区中的 shell 文件在打包后保留了 CRLF 换行。修复方式是在 Python 打包逻辑里把 `.sh` 文件统一转换成 LF。

部署过程中还曾出现 Windows 路径分隔符进入 tar 包的问题。远端 Docker 构建时找不到 `docker/entrypoint.sh`，因为包内路径变成了反斜杠形式。修复方式是在写入 tar 条目时强制使用 POSIX 风格的 `/`。

最初的魔改打包范围过大，包含了一些不参与运行的上游隐藏目录和测试目录。为了让部署更稳定，也为了方便开源，我把远端部署用的构建上下文收敛为最小集合，并在每次部署前清空远端旧源码目录。

最终验证结果显示，固定端和测试端的首页、双 VPS 页面和代理健康接口都能正常访问。双向测速也成功返回了下载、上传、延迟、抖动和 HTTP 请求失败率。早期报告曾把最后一项简称为丢包率，后续完备性检查已经纠正术语。

## 本地交互式脚本实现过程

用户后续要求“不登录两台机器也能知道结果”，因此我新增了 `new/interactive_vps_pair.py`。

这个脚本把日常操作拆成逐步交互。用户可以选择只健康检查、健康检查加测速、只测速、只部署固定端、只部署测试端或两端都部署。只有选择部署类动作时，脚本才会询问 SSH 密码并自动连接远端；如果只是检查和测速，脚本完全通过 HTTP 接口完成，不需要 SSH 登录。

交互式脚本会复用本地令牌文件 `new/.vps_token`。该文件保存代理访问令牌，用于访问两端受保护的 `vps-agent` 接口。报告不会写入令牌明文，只会写入令牌文件路径和令牌指纹。

交互式脚本经过一次本地验证。验证时选择“只做双向测速，不做健康检查，不部署”，连接已有固定端 A 和测试端 B，下载测试大小为 1 兆字节，上传测试大小为 1 兆字节，延迟采样 3 次，单项超时 20 秒。验证成功，并生成了本地报告。

## 中文化和开源整理过程

用户指出之前的文档不能只是命令结果堆叠，需要用中文自然语言完整概括信息。因此我新增了根目录 `README.md` 和 `docs` 目录，并开始把新增脚本的输出、报告模板和新增页面改成中文。

本次整理的目标是让第一次看到项目的人能够直接理解：项目从哪里来、改了什么、为什么这么改、怎么部署、怎么交互使用、怎么更换测试端、怎么判断结果、怎么避免泄露令牌和密码、怎么推送到 GitHub。

在 `2026-08-31 00:18 Asia/Shanghai` 左右做开源前复验时，我先从本地访问三个入口。独立官方原版服务返回 `200`，固定端 A 的 `/vps.html` 返回 `200`，但测试端 B 出现异常：根页面返回 `502 Bad Gateway`，双 VPS 页面和代理健康接口出现连接重置。这说明测试端当时并不满足高可用要求。

随后我没有重装两台机器，而是按项目设计使用“固定端不动，只恢复测试端”的方式处理。通过 `deploy_vps_pair.py --skip-fixed` 只重部署测试端后，测试端容器重新构建并通过本机代理健康检查。脚本随即执行一次小流量双向测速，固定端到测试端方向下载为 `60.77` 兆比特每秒、上传为 `931.01` 兆比特每秒，测试端到固定端方向下载为 `66.05` 兆比特每秒、上传为 `1613.43` 兆比特每秒，两个方向 HTTP 请求失败率均为 `0%`。

因为固定端当时仍然运行旧版本，返回的说明字段还有英文，我继续通过 `deploy_vps_pair.py --skip-target` 只重部署固定端。固定端更新后再次通过容器健康检查，并生成一份部署脚本报告。该次报告显示，固定端到测试端方向下载为 `66.91` 兆比特每秒、上传为 `130.81` 兆比特每秒，测试端到固定端方向下载为 `41.23` 兆比特每秒、上传为 `1660.12` 兆比特每秒，两个方向 HTTP 请求失败率仍为 `0%`。

最后我运行 `interactive_vps_pair.py`，选择“健康检查 + 双向测速，不部署”，也就是不 SSH 登录任何服务器，只通过 HTTP 接口完成检查。结果显示固定端和测试端的原版首页、双 VPS 页面、代理健康接口全部返回 `200`。该次交互式测速中，固定端到测试端方向下载为 `67.91` 兆比特每秒、上传为 `129.67` 兆比特每秒、平均延迟为 `4.068` 毫秒；测试端到固定端方向下载为 `42.65` 兆比特每秒、上传为 `1303.59` 兆比特每秒、平均延迟为 `3.252` 毫秒；两个方向 HTTP 请求失败率均为 `0%`。这证明当前本地交互式脚本能够在不手工登录两台机器的情况下给出可读的完整结果。
