## 第一阶段：理解原项目

在开始写代码之前，我先阅读了 LibreSpeed 的项目结构。重点确认了原项目的入口页面、浏览器测速工作线程、PHP 后端接口和官方 Docker 入口脚本。

阅读后得到的结论是：原版功能主要由 `speedtest.js`、`speedtest_worker.js` 和 `backend/` 目录支撑。下载、上传、延迟和 IP 获取都通过普通 HTTP 完成，因此服务器间测速可以复用原来的后端接口，而不需要引入新的测速协议。

我还确认了官方 Docker 镜像的启动方式。官方镜像会把 `/speedtest` 下的前端和后端文件复制到 `/var/www/html`，再启动 Apache。基于这个机制，魔改版只需要在镜像里追加新页面和新代理目录，并在入口脚本里多复制这两类文件。

## 第二阶段：官方部署脚本

最先编写的是 `shell_script/deploy_librespeed.sh`。它的目标是在一台授权 VPS 上部署原版 LibreSpeed，与增强版使用不同端口。实机地址和端口仅保存在本地私密审计，公开脚本默认使用通用的 `8080`，也可以通过 `PORT` 指定。

脚本的基本流程是：检查是否以 root 身份运行，创建 `/opt/librespeed` 目录，安装 Docker，拉取官方镜像，启动容器，然后访问本机端口做健康检查。

第一次远端执行时，Debian 13 默认软件源里没有 `docker-compose-plugin` 包，脚本因此中断。这个问题说明不能把 Docker Compose 插件当成必然存在的依赖。随后我修改脚本，让它在 Compose 可用时使用 Compose，不可用时自动退回到 `docker run`。第二次执行成功，原版服务通过了本机和外部 HTTP 检查。

## 第三阶段：魔改服务器间测速

魔改版代码放在 `new/project`。最初我复制了上游项目作为修改基础，随后把真正参与魔改部署的构建上下文收敛为少量必要文件。

核心新增文件是 `vps-agent/common.php`。它集中处理令牌验证、请求体解析、目标地址校验、下载测速、上传测速、延迟采样、节点名称读取、公开地址读取和远端 JSON 调用。

`vps-agent/health.php` 只负责健康检查。只要令牌正确，它就返回当前节点的代理版本、节点名、公开地址和原版 LibreSpeed 后端入口。

`vps-agent/measure.php` 负责单向测速。它接收一个目标地址，然后当前节点主动访问目标节点的 `backend/garbage.php` 和 `backend/empty.php`，计算吞吐和延迟。

`vps-agent/pair.php` 负责双向编排。它先让固定端测测试端，再带着同一个令牌调用测试端的 `measure.php`，让测试端反向测固定端，最后把两个方向合并成一份报告。

新增页面 `vps.html` 让用户可以在浏览器里输入固定端、测试端、令牌和测试参数，然后触发固定端的 `pair.php`。这个页面不保存令牌，只在当前请求中使用。

## 第四阶段：一键部署和交互式脚本

`new/deploy_vps_pair.py` 是非交互式脚本，适合明确知道参数时直接运行。它会在本地打包魔改项目的最小构建上下文，通过 SSH 上传到远端，在远端构建镜像并启动容器，然后执行双向测速并保存报告。

`new/interactive_vps_pair.py` 是后续新增的交互式脚本。它面向日常使用，把每一步拆开询问用户：选择动作、输入固定端、输入测试端、确认令牌、按动作输入必要参数、确认执行、保存报告。SSH 信息只在部署对应节点时出现。

交互式脚本支持只通过 HTTP 获取结果。也就是说，当两台 VPS 已经部署好时，它不需要 SSH 密码，也不会登录服务器。只有用户选择自动部署固定端或测试端时，才会临时询问 SSH 密码。

## 第五阶段：修复过程中发现的问题

第一个问题是 Windows 工作区中的 shell 脚本可能带有 CRLF 换行。远端 Docker 构建后，容器执行 `/entrypoint.sh` 时会出现无法识别回车符的问题。修复方式是在 Python 打包时把 `.sh` 文件统一转换为 LF。

第二个问题是 Windows 路径分隔符会进入 tar 包，导致远端 Docker 构建时找不到 `docker/entrypoint.sh`。修复方式是在写入 tar 条目时强制使用 POSIX 风格的 `/` 路径。

第三个问题是初始打包范围过大，包含上游项目中不参与魔改部署的隐藏目录和测试目录。修复方式是只打包魔改镜像真正需要的文件，并在远端部署前清空旧源码目录。

第四个问题是交互式脚本在管道输入不足时，保存失败报告时又触发二次异常。修复方式是让输入暂停步骤在遇到输入结束时自动继续，同时让报告生成逻辑能处理没有测速摘要的失败场景。

## 第六阶段：中文化和开源整理

根据后续要求，我把新增脚本、报告模板、双 VPS 页面和开源文档改为中文表达。新的报告不再只罗列命令输出，而是用自然语言说明脚本做了什么、每个结果代表什么、失败时应该看哪里。

同时增加了根目录 README 和 `docs` 目录，专门解释原理、编码过程、操作审计、高可用设计和 GitHub 上传步骤。公开仓库会忽略令牌文件、缓存文件、临时压缩包和日志，避免泄露运行凭据。

## 第七阶段：完备性复验后的结构修正

第二轮完备性审查不以“当前能跑”为标准，而是检查新用户、失败路径和未来更换测试机的行为。审查发现，只测速模式仍会在模块导入时强制加载 Paramiko；两端只能共用 SSH 配置；命令行参数缺少严格范围；某个子指标失败时顶层仍可能显示成功。

Paramiko 随后改为部署时按需导入。交互脚本按动作跳过无关输入，并允许固定端和测试端分别使用不同端口、用户和密码。命令行端口、数据量、采样次数和超时都增加上下限。结果摘要逐层检查正反方向的下载、上传和延迟，不再只相信顶层 `status`。

代理正确性审查还发现，curl 默认会把 HTTP 404 当成正常命令退出。修复后，下载、上传和延迟都要求目标 HTTP 状态处于成功范围。故意访问不存在路径时三项全部返回 `error`，证明错误页不再被当作测速数据。

为了控制资源，`pair.php` 和 `measure.php` 增加单节点非阻塞任务锁。第二个并发请求返回 409。令牌只允许放在请求头，移除了 URL 参数回退，并补充浏览器跨域预检响应。

## 第八阶段：可恢复部署

原部署逻辑在启动新版本前删除旧容器。如果候选镜像启动失败，服务会直接中断。最终逻辑先构建 `next` 镜像，此时旧容器继续工作；切换前把当前镜像保存为 `rollback`；候选健康失败时尝试恢复旧镜像。

基础镜像也从 `latest` 改为固定 GHCR 内容摘要，避免未来上游变化导致相同代码构建出不同结果。两端成功切换路径已经真实验证，失败回滚分支没有在生产端做破坏性注入。

## 第九阶段：Windows 和文档完备性

PowerShell 5.1 实测暴露了中文无 BOM 文件解析失败。包装脚本最终采用 UTF-8 BOM 和 CRLF，并自动寻找三种常见 Python 命令。

README 按零基础阅读顺序重写，新建完整文件总览和测试验收文档。旧文档中关于 SSH、旧报告、`latest` 镜像和“丢包率”的过期描述同步修正。HTTP 延迟采样失败比例现在明确称为“HTTP 请求失败率”，避免冒充 ICMP 丢包。

本地健康检查还增加服务器时钟偏差。实测两台 VPS 均未启用 NTP，报告会给出警告，但本轮没有擅自修改服务器系统时间。

## 第十阶段：公开前的启动与隐私整改

先编写启动回归测试，确认未实现的环境准备模块会失败，再补代码。根目录新增 `start.cmd`、`start.sh` 与 `start.py`：前两个只包装平台启动，后者用脚本自身位置定位项目，不依赖用户从哪个目录打开，也支持目录含空格。Windows 旧 PowerShell 入口转到统一入口，继续保留中文 BOM。

`new/prepare_runtime.py` 仅用标准库。它把确认、创建虚拟环境、限时安装固定依赖、验证导入和重新打开向导串起来。只有原向导的部署动作加载 Paramiko 失败时才调用；安装失败不伪装成成功，取消不产生文件，不覆盖已有不完整目录，也不改变服务器。

完整性测试补上虚拟环境与私密备份的忽略检查，并检查自有文档及脚本中的 IPv4 仅使用文档保留段或本机回环地址。上游源码单独保留，避免误删合法署名、示例和公开第三方服务。维护者仍需用仅本地保存的实际敏感值扫描最终发布包及提交元数据，自动测试不是任意隐私检测器。

README 以“下载、安装 Python、双击启动、逐步确认”叙述；上传文档取消全目录暂存示例，强调私有验收、指定文件暂存、noreply 邮箱与匿名访问检查。八份可识别机器的历史文档改为匿名叙述，单机默认端口及测试样例改为通用端口。所有原始内容已先备份，不以删除审计的方式隐藏历史问题。
