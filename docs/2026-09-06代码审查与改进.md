# 2026-09-06 代码审查与改进

## 审查结论

本轮审查从已发布 `948b19f` 开始，重点是“用户怎样输入、请求实际会做什么、失败后恢复哪份状态、报告是否如实解释”，不是格式整理。确认的问题均在本轮修复并加入相应验证；没有把潜在想法直接塞入产品，也没有改写原版 LibreSpeed 核心算法。

| 优先级 | 旧行为与实际风险 | 修复位置及验证 |
| --- | --- | --- |
| 高 | HTTP 自动跳转可能把令牌带到其他地址；反向接口的错误 HTTP 状态可能被成功 JSON 掩盖 | 两个 Python 控制器与 `vps-agent/common.php` 禁止跳转并核验状态；本地双 HTTP 服务及 PHP 测试确认目标未收到令牌 |
| 高 | 升级失败仅恢复旧镜像，却使用新端口、新令牌和新环境，可能无法恢复原服务 | 新 `deploy_node.sh` 保存并恢复原容器；真实 Bash 加 Docker 状态替身的四条路径对比原配置 |
| 高 | 网页把远端错误直接放进 innerHTML，持有令牌的恶意节点可能注入页面内容 | `vps.html` 改为 DOM 文本赋值；桌面/手机注入字符串测试确认没有生成图片节点或执行事件 |

| 中 | 响应回显令牌会进入报告，JSON 转义可能绕过字面替换 | Python、PHP 和网页逐层处理已解码数据；普通与带引号令牌回显测试通过 |
| 低 | 作者机器写死为默认值，新手可能误操作；报告只讲方向容易看反 | 地址必须自己填，可选择保存本地节点配置；README 改为虚构 A/B/C，单列四次数据流向 |
| 低 | 打包异常留下临时文件、同秒报告重名、流量单位笼统 | 异常清理与唯一任务目录；报告名带微秒；统一 MiB 并显示双向预算 |
| 中 | 部署后的二次上传包清理遇到断网，可能掩盖实际部署成功，导致交互层漏记节点与令牌保存 | 远端自身仍清理，控制器二次确认失败只给警告；回归测试确认成功状态不会被覆盖 |

高优先级表示可能泄露访问权限或破坏恢复能力，不意味着已经确认发生外部攻击。网页风险需要可控的远端响应，接口风险需要对应请求条件；不夸大为所有访问者都可任意执行命令。

## 从问题产生的改进思路

第一项是“固定端长期保留，测试端常换”的记忆式输入。不是增加节点数据库，而是一个版本化本地 JSON，仅保存用户选择的地址、端口、协议和 SSH 用户名。这样只换测试端就能复用固定端，仍逐项确认；损坏配置必须报错，不能替用户猜节点。

第二项是执行前的流量账。下载 64 MiB、上传 32 MiB，看上去像 96 MiB，其实两个方向共四次传输，是 192 MiB；每端发送和接收各约 96 MiB。脚本和网页都先说明预算，报告再解释实传字节。它是可见的预估，不是伪装成云账单配额控制器。

第三项是“恢复配置而不只是恢复版本”。镜像相当于安装包，容器还包含端口、钥匙和挂载。保留原容器比自行拼回每一个 Docker 参数更简单、更容易核验。代价是切换时仍有短暂停机，且只保留本次切换窗口，不承诺跨版本任意回溯。

第四项是让失败报告也能用于判断。取消、未启动、未完成分开描述；成功项不因另一项失败而消失；过短测量提醒增大样本。未增加自动重测、常驻控制服务或复杂历史图表，避免改变逐步交互和可预知流量的需求。
