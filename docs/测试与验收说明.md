新增质量门槛包含：输入结束不放行；首次取消不写配置/令牌且不登录；日常健康检查不 SSH；健康失败不发测速 POST；重定向不转发令牌；POST 超时不重复测速；畸形数据不崩溃；配置损坏不静默使用；四条部署状态路径；PHP 错误页面/字节/协议/令牌检查；桌面手机表单、报告导出、复制和错误文本安全显示。

## 这份文档解决什么问题

本文件说明项目测试了什么、怎么测试、什么结果才算通过，以及目前仍然没有被实验证明的部分。它的作用不是堆放终端输出，而是让后来维护的人能够用相同条件复验。

本轮验收日期是 `2026-08-31`，本地工作区是 Windows，Python 版本是 `3.14.2`，自动部署依赖 Paramiko 版本是 `5.0.0`。固定端运行 Debian 13，测试端运行 Debian 12。两端 SSH 端口、Web 端口和公网地址由本项目现有配置提供。

## 验收目标

项目只有同时满足以下条件，才算具备可交付状态：

1. 原版 LibreSpeed 服务不能因为魔改功能而消失。
2. 两端都必须能完成下载、上传、延迟、抖动和请求失败率测量。
3. 用户在“只检查和测速”时不能被迫安装 SSH 依赖或输入 SSH 密码。
4. 固定端和测试端必须允许使用不同 SSH 端口、用户和密码。
5. 错误令牌、错误页面和部分指标失败不能显示为成功。
6. 同一节点不能无限并发执行大流量测试。
7. 新镜像构建失败时不能提前删除仍在工作的旧容器；切换后健康失败必须有恢复旧镜像的路径。
8. 令牌和真实运行报告不能进入公开 Git 仓库。
9. 所有执行结果都要有中文自然语言报告和机器可读 JSON。

## 本地自动测试

运行命令：

```powershell
python -B -m unittest discover -s tests -v
```

测试覆盖以下行为：

- 部署压缩包只包含实际构建需要的文件。
- tar 包内部使用 Linux 的 `/` 路径，不出现 Windows 反斜杠。
- 远端入口 Shell 在压缩包中使用 LF 换行。
- 命令行参数超出允许范围时立即拒绝。
- 单端部署或纯测速缺少现有令牌时立即拒绝，只有两端同时部署可以自动生成令牌。
- 本地双向请求的总超时覆盖两个方向的最坏执行时间。
- 只有两个方向的下载、上传和延迟都成功时，报告才标记为成功。
- 后端顶层状态错误或某个隐藏指标失败时，摘要必须标记失败。
- 服务器时钟偏差超过 30 秒时，健康报告必须给出警告。
- Markdown 报告不包含令牌明文。
- Git 跟踪文件必须包含关键交付物，不能包含令牌、真实报告、缓存或错误换行的 Shell 文件。
- README 中所有仓库内相对链接必须指向真实存在的文件。
- 实际部署 Dockerfile 必须固定官方基础镜像摘要，不能继续引用 `latest`。
- 候选容器连启动命令都失败时，生成的远端脚本仍必须进入旧版本恢复分支，不能被 `set -e` 提前终止。
- 没有执行的健康检查或测速必须写成“未执行”，不能伪装成“通过”。
- 两端部署中途失败时，失败报告必须保留已经成功部署的节点，不能丢失部分进度。

此外运行了不加载第三方站点包的导入测试：

```powershell
python -S -B -c "import pathlib,sys; sys.path.insert(0,str(pathlib.Path('new').resolve())); import interactive_vps_pair; print('paramiko' not in sys.modules)"
```

结果为 `True`。这证明健康检查和测速模式只依赖 Python 标准库。Paramiko 只有在用户真正选择远端部署时才会按需加载。

## Windows 包装入口测试

最初复验 `new/interactive_vps_pair.ps1` 时，Windows PowerShell 5.1 把无 BOM 的中文 UTF-8 文件按本地代码页解释，最终报出字符串缺少结束引号。这不是 Python 逻辑错误，而是 PowerShell 5.1 的文件编码识别问题。

修复后，包装脚本使用 UTF-8 BOM 和 CRLF。实测命令为：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File new\interactive_vps_pair.ps1
```

包装脚本能够正确显示中文，按顺序查找 `py`、`python` 和 `python3`，并把 Python 脚本退出码原样返回。

## 两端部署测试

两端都使用 `new/deploy_vps_pair.py` 部署代理版本 `1.2.0`。部署过程先把最小构建上下文上传到 `/opt/librespeed-vps`，再基于固定摘要的官方镜像构建候选镜像。

观察到的关键行为如下：

- 候选镜像构建时，旧容器没有提前删除。
- 基础镜像摘要能够在两端解析并构建。
- 切换前，当前镜像被标记为回滚镜像。
- 候选容器刚启动时出现过一次短暂连接重置，脚本继续等待，没有立即误判失败。
- 数秒后两端令牌健康接口通过，部署才返回成功。
- 固定端和测试端都使用 `--restart unless-stopped`。
- 部署完成后自动执行 8 MB 下载、4 MB 上传、5 次延迟采样的小流量双向检查，两个方向状态均为 `ok`。

本轮没有故意构造坏镜像去破坏线上容器，因此“健康失败后自动恢复旧容器”的分支已经完成代码审查和 Shell 语法验证，但没有在这两台正在使用的服务器上做破坏性故障注入。README 和高可用文档不会把这一项描述成已经实战触发过。

- 独立官方原版：根路径 `/`。
- 固定端 A 增强版首页：根路径 `/`。
- 固定端 A 双 VPS 页面：`/vps.html`。
- 测试端 B 增强版首页：根路径 `/`。
- 测试端 B 双 VPS 页面：`/vps.html`。

上述为匿名实测记录，实际地址、端口和凭据不公开，不提供可直接使用的测试服务器。

两端受保护健康接口使用正确令牌时返回 HTTP `200` 和代理版本 `1.2.0`。使用故意错误令牌时，两端都返回 HTTP `401`。

浏览器跨域预检请求返回 HTTP `204`，允许 `Content-Type` 和 `X-LibreSpeed-Token` 请求头。令牌不再接受 URL 查询参数形式。

为了确认“错误页面不会被当作高速下载”，测试把目标指向一个确定不存在的 LibreSpeed 根路径。固定端返回的总体状态为 `error`，下载、上传和延迟三项也全部为 `error`。这证明 HTTP `404` 或错误正文不会再被按成功传输计算。

## 并发保护测试

测试程序先向固定端发起一次真实双向测速，在第一个请求仍持有节点锁时，再发起第二个完全相同的请求。

第一个请求最终返回 `ok`；第二个请求立即返回 HTTP `409`。这证明同一节点同一时刻只执行一个测速任务，不会因为连续点击或多个客户端同时操作而无限叠加流量。

## 时钟检查结果

健康接口返回服务器 UTC 时间，本地脚本会计算服务器时间和本地时间的近似偏差。最终交互测试发现：

- 固定端约落后本地 `252.8` 秒。
- 测试端约落后本地 `188.2` 秒。

随后通过 SSH 只读执行 `timedatectl show`，两端都显示 `NTP=no`、`NTPSynchronized=no`，`systemd-timesyncd` 为 `inactive`。两台服务器的 RTC 时间更接近本地，而系统时间落后。

本项目用各节点自己的高精度耗时测量传输持续时间，因此时钟偏差不会直接改变 Mbps 和单次往返耗时；但跨节点的绝对时间戳不能用于严格排序。为了避免影响服务器上的其他未知业务，本轮只记录问题，没有执行 `timedatectl set-time` 或启用 NTP。

## 以后如何复验

每次修改核心代码后至少完成以下顺序：

1. 运行本地单元测试，确认没有失败。
2. 使用 `python -S` 验证不部署模式仍不依赖 Paramiko。
3. 只部署测试端，确认固定端没有被重启。
4. 检查两端首页、双 VPS 页面、正确令牌和错误令牌。
5. 用不存在路径验证错误结果不会显示成功。
6. 用两个并发请求验证第二个返回 `409`。
7. 运行交互模式 `2`，使用至少 64/32 MB 生成最终报告。
8. 检查 `git status --short --ignored`，确认令牌和真实报告只显示为 ignored。
9. 推送后检查 GitHub Actions 和远端提交号。
