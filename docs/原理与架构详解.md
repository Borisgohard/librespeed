# 原理与架构详解

## 原版 LibreSpeed 的测速原理

LibreSpeed 的原版设计很轻量。浏览器打开网页后，前端会启动一个 Web Worker，由这个工作线程负责发起 HTTP 请求并计算结果。它不依赖 Flash、Java 或 WebSocket，核心逻辑都是普通 HTTP 请求。

原版的下载测速，是浏览器并发请求服务端的 `backend/garbage.php`。这个接口会生成随机数据块并持续返回给浏览器。浏览器根据收到的数据量和耗时计算下载速度。

原版的上传测速，是浏览器把一段测试数据通过 POST 请求发给 `backend/empty.php`。这个接口不会保存数据，只负责尽快返回空响应。浏览器根据上传的数据量和耗时计算上传速度。

原版的延迟和抖动测试，并不是 ICMP ping。浏览器不能直接通过 HTTP 页面发 ICMP 包，所以 LibreSpeed 使用多次 HTTP 空请求来估算往返延迟。脚本反复请求 `backend/empty.php`，记录每次请求从发出到收到响应的时间，再计算平均延迟和延迟抖动。

原版的 IP 信息来自 `backend/getIP.php`。这个接口会读取访问者的 IP，如果配置了第三方或离线数据库，还可以返回运营商和地理位置信息。

## 本项目新增的服务器间测速

用户最初的需求不是只测“本地电脑到 VPS”，而是希望知道“两台 VPS 之间”的线路质量。这个需求不能单纯依赖原版网页测速，因为网页测速的发起方永远是浏览器所在的本地设备。

本项目新增了一个受令牌保护的代理层，目录是 `new/project/vps-agent/`。这个代理层运行在每台 VPS 上。固定端收到本地脚本发来的请求后，会先从固定端主动测测试端，再调用测试端的代理接口，让测试端反向测固定端。

因此，一次完整双向测试包含两个方向：

```text
固定端 VPS  ->  测试端 VPS
测试端 VPS  ->  固定端 VPS
```

每个方向都包含下载、上传、平均延迟、延迟抖动和 HTTP 请求失败率。这里的失败率来自延迟采样请求，不是 ICMP 协议层的严格丢包率。

## 请求链路

本地交互式脚本发起测试时，先把固定端和测试端地址、测试参数、代理访问令牌一起提交给固定端：

```text
本地电脑  ->  固定端 /vps-agent/pair.php
```

固定端执行第一组测试：

```text
固定端  ->  测试端 /backend/garbage.php   用于下载测速
固定端  ->  测试端 /backend/empty.php     用于上传测速和延迟采样
```

固定端随后调用测试端代理，让测试端反向执行同样的测试：

```text
固定端  ->  测试端 /vps-agent/measure.php
测试端  ->  固定端 /backend/garbage.php
测试端  ->  固定端 /backend/empty.php
```

测试端把反向结果返回给固定端，固定端再把完整双向报告返回给本地脚本。

## 新增接口说明

`/vps-agent/health.php` 用于健康检查。它验证代理访问令牌是否正确，并返回当前节点名称、公开地址、代理版本和原版 LibreSpeed 后端入口地址。

`/vps-agent/measure.php` 用于执行单向测速。调用方传入目标地址后，当前节点会从目标地址下载随机数据、上传测试数据，并用 HTTP 空请求采样延迟。

`/vps-agent/pair.php` 用于双向编排。它只需要本地脚本调用固定端一次，就能拿到固定端到测试端、测试端到固定端两个方向的完整结果。

## 为什么保留 Docker

官方 LibreSpeed 的运行环境是 Web 服务器加 PHP。为了降低远端系统差异带来的部署风险，本项目继续使用 Docker。魔改版镜像基于官方镜像构建，只覆盖入口脚本、两个入口页面和新增代理目录。

这样做有两个好处。第一，原版功能继续由官方镜像提供，不需要重新维护整套 Apache 和 PHP 运行环境。第二，新增功能只集中在少量文件中，后续升级官方镜像时，维护成本更低。

## 固定端和测试端的角色

固定端是长期保留的一端，通常部署在你最常用或最信任的 VPS 上。测试端是经常更换的一端，用来比较不同 VPS 到固定端的链路质量。

更换测试端时，只需要把同一份魔改服务部署到新测试端，并让它使用和固定端一致的代理访问令牌。固定端不需要重新部署，除非固定端代码或令牌发生变化。

## 安全边界

服务器间测速会占用两端带宽，因此不能做成公开接口。本项目要求所有 `/vps-agent/` 接口都携带 `X-LibreSpeed-Token` 请求头。令牌不写入公开页面，也不写入报告正文。报告只记录令牌文件路径和令牌指纹，用来确认两端是否使用同一个令牌。

令牌不再允许通过 URL 查询参数传递，因为 URL 更容易进入浏览器历史、代理日志和访问日志。代理支持浏览器 `OPTIONS` 预检，但实际业务请求仍必须带正确令牌。

当前演示服务使用 HTTP，令牌请求头没有传输加密。令牌认证只能防止不知道令牌的人直接调用，不能防止链路窃听。正式部署应加 HTTPS，并限制来源地址。

## 成功判定

下载和上传使用 curl。curl 即使收到 404 也可能以零退出码结束，所以项目不能只看进程退出状态。1.3.0 只接受 200 到 299，不跟随跳转。下载字节数必须等于请求的 MiB 乘以 1048576；上传发出字节数也必须匹配，并要求目标返回空响应。HTTP 200 的错误网页不再被当成正确的测速数据。

延迟采样使用同样的 curl 指标格式，每次失败都会计入 `lossPct`。该字段为了兼容早期报告继续保留，但语义是“HTTP 请求失败百分比”，不是 ICMP 数据包丢失百分比。

一个方向只有下载、上传和延迟都成功才是 `ok`。双向结果只有固定端到测试端、测试端到固定端都成功才是 `ok`。本地脚本还会再次逐项验证，避免服务端顶层状态错误掩盖子项失败。

## 并发和超时

每个节点使用一个本地文件锁。`pair.php` 或 `measure.php` 开始时尝试非阻塞获取锁，已有任务时返回 409。固定端和测试端各自持有自己的锁，所以正常双向测试仍可以按设计串联执行。

下载和上传各有单项超时，延迟单次请求最多等待三秒。固定端调用测试端反向测量时，会根据两个传输超时、采样次数和缓冲时间计算单方向上限。本地脚本再按两个方向计算总等待时间，避免正常慢链路被本地过早断开。

## 部署数据流

本地部署脚本不会上传整个上游源码目录。它把 Dockerfile、两套入口页面、双 VPS 页面、入口 Shell 和四个代理 PHP 文件打成最小 tar 包，通过 SFTP 上传。

远端先构建候选镜像，旧容器此时继续提供服务。候选构建成功后，当前镜像被标记为回滚版本，旧容器改名保留后才停止并切换。新容器只有通过带令牌的健康检查才成为当前版本；失败时恢复原容器本身，而不是拿新端口、新令牌去启动旧镜像。这样原环境变量和挂载也能保留。成功后清理旧容器和本次临时构建目录，回滚镜像标签继续保留。

官方基础镜像使用内容摘要固定。这样牺牲自动追随 `latest` 的便利，换取部署结果可重复。上游升级必须成为一个明确、可测试的维护动作。

## 1.3.0 的控制与报告边界

本地是一次性控制程序，不是流量中转站。只读 GET 检查仅在连接失败或 502、503、504 时有限重试；POST 测速不自动重试，因为响应超时不代表服务器任务没有启动。健康数据还要验证代理 JSON 结构，不能把普通网站的 200 页面看成节点就绪。

固定端、测试端是发起测量的角色，不是固定的数据流向。固定端“下载”时实际数据来自测试端，固定端“上传”时才发往测试端。四次文件传输合计有效流量为两倍的下载大小加上传大小，1.3.0 会在最终确认前明示预算。

本地、反向 PHP 请求和浏览器请求都不跟随 HTTP 跳转传送令牌。原版公开后端仍保留；代理令牌不是站点级访问控制。部署者必须自行决定防火墙或 HTTPS 方案，本轮没有声称完成证书管理和公网限流。
