# 魔改操作过程留痕

本文件记录双 VPS 魔改项目的实际实现和验证过程。

实现开始时，我把上游 LibreSpeed 项目复制到 `new/project` 作为修改基础。这样做的目的是先保留完整上下文，避免误删原版功能。后续部署时，我又把真正上传到远端的构建上下文收敛为最小必要文件，避免把无关隐藏目录、测试目录和临时内容带到服务器。

魔改镜像的 `Dockerfile` 最初基于官方镜像 `ghcr.io/librespeed/speedtest:latest` 构建。完备性复验时发现 `latest` 会随上游更新而漂移，最终改为固定官方镜像内容摘要。镜像只额外复制修改后的入口脚本、两个入口页面、新增的双 VPS 页面和新增的代理接口目录。这样既能继承官方 Apache 和 PHP 运行环境，也能让魔改代码保持清晰且可重复构建。

入口脚本 `docker/entrypoint.sh` 在官方逻辑基础上增加了两项复制操作：把 `vps.html` 放到 Web 根目录，把 `vps-agent` 目录也放到 Web 根目录。容器启动后，原版 LibreSpeed 首页和新增双 VPS 页面会同时可用。

我新增了四个代理文件。`common.php` 保存通用逻辑，负责令牌验证、输入解析、目标地址检查、测速执行和远端 JSON 调用。`health.php` 用于健康检查。`measure.php` 用于执行单向服务器间测速。`pair.php` 用于把固定端到测试端、测试端到固定端两个方向组合成一份报告。

我还新增了 `vps.html` 页面。这个页面允许用户输入固定端地址、测试端地址、代理访问令牌和测试参数，然后触发双向测试。页面显示下载速度、上传速度、平均延迟、延迟抖动和 HTTP 请求失败率，并提供完整 JSON 结果复制能力。

实机部署使用已授权固定端 A 和测试端 B，地址和端口不公开。两端容器都命名为 `librespeed-vps`，都使用 Docker 自动重启策略。固定端独立原版 LibreSpeed 使用另外一个端口，没有被增强服务覆盖，仍然继续运行。

过程中修复了三个关键问题。第一，Windows 工作区中的 shell 脚本带有 CRLF 换行，导致容器入口脚本在 Linux 中无法执行；修复方式是在打包阶段把 `.sh` 文件统一转换为 LF。第二，Windows 路径分隔符进入 tar 包，导致远端构建找不到 `docker/entrypoint.sh`；修复方式是写入 tar 条目时强制使用 `/`。第三，初始打包范围过大；修复方式是只打包魔改镜像真正需要的文件，并在远端部署前清理旧源码目录。

最终远端 `/opt/librespeed-vps/src` 只保留构建和运行魔改功能所需的文件：`Dockerfile`、`docker/entrypoint.sh`、`index-classic.html`、`index-modern.html`、`vps.html` 以及 `vps-agent` 目录。固定端和测试端的容器健康检查都已经通过。

完备性检查又发现了三个结果正确性问题。旧代码只判断 curl 是否退出成功，没有检查 HTTP 状态，因此 404 页面可能被误算成成功；延迟请求也没有严格确认 HTTP 成功；双向顶层状态可能在某个子指标失败时仍写成 `ok`。代理版本 `1.2.0` 统一要求 HTTP 成功状态，并逐层汇总三个指标和两个方向。

为了避免重复点击造成并发大流量，`pair.php` 和 `measure.php` 增加每节点单任务锁。真实并发测试中，第一个请求完成，第二个同时请求返回 `409`。

部署流程也从“删除旧容器再启动新版本”改为“先构建候选镜像、保存当前镜像、再切换、健康失败则恢复旧镜像”。两端成功升级路径已经实测。失败回滚分支没有在生产端故意注入坏版本，所以只记录为已实现但未做破坏性演练。

最终代理版本为 `1.2.0`。两端正确令牌健康检查返回 `200`，错误令牌返回 `401`，不存在后端路径会把下载、上传和延迟全部标记为 `error`。
