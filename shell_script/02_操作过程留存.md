# 操作过程留存

本文件记录官方 LibreSpeed 服务从本地准备到远端部署成功的完整过程。记录采用中文自然语言概括，不把命令输出原样堆进正文。

开始时，我先检查本地项目工作目录。目录为空，并且不是 Git 仓库。随后我检查本机可用工具，确认 Git、Windows OpenSSH 的 `ssh` 和 `scp` 都可用；本机没有 `sshpass` 和 `plink`，但 Python 的 `paramiko` 库可用，因此远端自动执行采用 Paramiko 完成。SSH 密码只在执行过程中使用，没有写入脚本或文档。公开副本不保留个人绝对路径。

随后我浅克隆了 GitHub 上的 `librespeed/speedtest` 仓库到本地临时目录 `.upstream_speedtest`。我阅读了项目说明、Docker 文档、官方 Dockerfile、官方入口脚本、前端测速控制逻辑、测速工作线程和 PHP 后端接口。阅读后确认：下载测速由 `backend/garbage.php` 返回随机数据，上传测速由 `backend/empty.php` 接收 POST 数据，延迟和抖动由多次请求 `backend/empty.php` 计算，IP 信息由 `backend/getIP.php` 返回。官方 Docker 镜像支持单机、后端、前端和双模式部署。

部署前，我探测了两台授权服务器。一个环境尚未安装 Docker，另一个环境已经安装 Docker 和 Docker Compose，因此验证同时涉及安装与复用两种情况。官方原版 LibreSpeed 只部署到固定端的独立端口。公开记录隐去两端地址、SSH 端口、实际 Web 端口及机器与系统版本的对应关系；完整原始信息保留在本地私密审计。

第一次执行官方部署脚本时，脚本在 Docker 安装阶段失败。失败原因不是网络问题，而是 Debian 13 默认软件源中找不到 `docker-compose-plugin` 包。这个结果说明脚本不应该把 Docker Compose 插件当成必须存在的依赖。随后我修改脚本，使它在 Compose 可用时使用 Compose，不可用时自动回退到 `docker run`。

第二次执行部署脚本时，Docker 安装成功，官方镜像 `ghcr.io/librespeed/speedtest:latest` 拉取成功，镜像摘要为 `sha256:93e8dba9dcb0698006b6175d2135b80970c138bfa15aea39156e5b23d289ed06`。因为该环境仍没有 Compose 插件，脚本按预期回退到 `docker run`，启动了名为 `librespeed` 的容器，并把用户指定的宿主机端口映射到容器内 `8080` 端口。

服务启动后，我先在远端本机访问所配置的 Web 端口，得到正常 HTTP 响应；随后从本地通过公网访问同一服务，同样得到 `HTTP 200`。容器日志显示 Apache 和 PHP 正常启动，没有持续报错。至此，当次官方原版 LibreSpeed 服务已完整部署并可以访问。

最终实际访问地址仅保存在本地私密记录，不提供公共测试端点。远端部署日志保存在 `/opt/librespeed/deploy.log`，容器日志可以通过 `docker logs -f librespeed` 查看。

第二轮完备性检查时，该在线服务仍返回 HTTP `200`，没有被双 VPS 魔改服务覆盖。上面记录的 `latest` 和旧摘要是首次实际部署时的历史事实；当前脚本默认值已经改为固定的新摘要，但本轮没有为了更新摘要而无必要重启仍然正常工作的原版容器。
